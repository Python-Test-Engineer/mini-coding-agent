# Chapter 02 - Lifecycle hooks and an observable agent loop

Chapter 01 built a small coding agent: a model requests tools, the Python host
runs them, and tool results return to the model. The loop works, but it is hard
to extend cleanly when every new feature must be inserted directly into the
middle of `agent_loop()`.

This chapter adds **lifecycle hooks**. A hook is a named callback that runs at a
defined point in the host-controlled agent lifecycle. Hooks are useful for
observing an agent, recording metrics, adding audit events, playing a sound, or
connecting later workshop exercises without rewriting the loop.

The goal is not to give callback code control over the agent. The host still
owns model requests, tool execution, error handling, and console rendering.
Hooks receive information about the transition and can react to it.

After this chapter the new or changed files are:

| File | Change from Chapter 01 |
| --- | --- |
| `src/lifecycle.py` | New `Hooks` base class that documents every callback point. |
| `src/agent.py` | Creates a context for each turn and calls hooks around the model/tool loop. |
| `src/ui.py` | Adds Rich rendering methods for lifecycle trace lines and hook failures. |
| `src/ui.json` | Adds the wording, ASCII icons, and styles for lifecycle events. |
| `tests/test_004_agent_lifecycle.py` | Verifies callback order, context, UI output, and hook-failure isolation. |
| `src/sandbox.py` | Adds separate read/write path rules, JSONL event logging, and a constrained command runner. |

## Why hooks belong at lifecycle boundaries

Without hooks, an extra feature is tempted to reach into unrelated places in
the loop:

```python
# This quickly makes the loop difficult to read and test.
save_audit_record(prompt)
reply = chat(messages)
save_model_response(reply)
result = TOOLS[name](**args)
save_tool_result(result)
```

The loop should instead announce the transitions it already performs:

```text
request
  -> before_input
  -> before_loop
  -> before_brain_request
  -> after_brain_response
  -> before_tool_execute / after_tool_execute (zero or more times)
  -> after_loop
  -> after_input
```

This makes three responsibilities clear:

| Responsibility | Owner |
| --- | --- |
| Deciding when an event happened and executing tools | `agent.py` |
| Reacting to an event | A `Hooks` subclass |
| Choosing how an event looks in the terminal | `UI` and `ui.json` |

For example, a hook can count completed tools, but it does not replace the
tool result that is sent back to the model. That keeps the model/tool protocol
in one trustworthy place: the host loop.

## The hook contract in `src/lifecycle.py`

`lifecycle.py` contains a small base class. On Windows, its session-start hook
plays `%WINDIR%\Media\Windows Logon.wav` asynchronously when the file exists.
Other methods are no-ops by default, so a subclass only overrides the callbacks
it needs. The default `SandboxAuditHooks` calls the base session-start hook
before writing its session log entry.

```python
class Hooks:
    def before_tool_execute(self, agent, tool_name, arguments):
        """Called before a requested tool is executed."""

    def after_tool_execute(self, agent, tool_name, result):
        """Called after a requested tool finishes, including failures."""
```

The `agent` parameter is an `AgentContext` created for one call to
`agent_loop()`. It exposes state that is useful to an observer:

| Context attribute | Meaning |
| --- | --- |
| `request` | The original user request text. |
| `messages` | The live message list that will be sent to the model. |
| `metrics` | The token and cost dictionary used by the footer. |
| `ui` | The active UI instance. A hook normally should not render directly. |
| `workspace` | The file-path policy and JSONL lifecycle event log. |
| `step` | The current one-based model-response step. |

The current lifecycle callbacks are:

| Callback | Called when | Extra arguments |
| --- | --- | --- |
| `on_session_start` | The interactive conversation starts. | None |
| `on_session_stop` | The interactive conversation ends. | None |
| `before_input` | A request starts processing. | `user_input` |
| `after_input` | A request has finished processing. | `user_input`, `output` |
| `before_loop` | The model/tool loop begins. | None |
| `after_loop` | The model/tool loop ends. | `output` |
| `before_brain_request` | Just before `chat(messages)`. | `conversation` |
| `after_brain_response` | Just after a model reply is read. | `thought` |
| `before_tool_execute` | Just before a requested tool runs. | `tool_name`, `arguments` |
| `after_tool_execute` | Just after that tool returns or fails. | `tool_name`, `result` |
| `on_error` | The host catches a tool or tool-argument error. | `error`, `phase` |

The base class also reserves `before_compact`, `after_compact`,
`on_mode_change`, and `on_brain_switch`. They are not fired by the Chapter 02
agent because it does not compact context, support modes, or switch providers.
Keeping their names in one documented contract gives later chapters stable
places to add those features.

## Calling hooks from the agent loop

`agent.py` imports the contract and creates a default instance:

```python
from sandbox import SandboxAuditHooks

# The default hook records sandbox session, tool, and caught-error events.
hooks = SandboxAuditHooks()
```

The `agent_loop()` function also accepts `lifecycle_hooks`. This makes tests and
other Python callers independent of the module-level default:

```python
def agent_loop(
    prompt: str,
    max_steps: int = 8,
    lifecycle_hooks: Hooks | None = None,
) -> None:
    active_hooks = lifecycle_hooks if lifecycle_hooks is not None else hooks
```

At the start of a turn, the agent builds its messages and context, then reports
the first two transitions:

```python
context = AgentContext(prompt, messages, metrics, ui, WORKSPACE)
_call_hook(active_hooks, "before_input", context, prompt, detail="...")
_call_hook(active_hooks, "before_loop", context, detail="...")
```

Before each request, the loop gives the hook the same `messages` list it is
about to pass to `chat()`. After the reply, it gives the hook the provider
message dictionary. The hook therefore sees the actual conversation state and
tool calls, not a copied or reconstructed version.

For each requested tool, the sequence is:

```python
_call_hook(active_hooks, "before_tool_execute", context, name, args)
try:
    result = TOOLS[name](**args)
except Exception as error:
    _report_error(active_hooks, context, error, "tool_execute")
    result = f"ERROR: {error}"
_call_hook(active_hooks, "after_tool_execute", context, name, result)
```

`after_tool_execute` runs whether the tool succeeded or failed. That is useful
for monitoring because an audit record can show both the requested action and
its final outcome.

### Hook failures are contained

Extensions should not make the coding agent unusable. `_call_hook()` catches an
exception raised by a callback and asks the UI to show a lifecycle-hook error
panel. It then continues the host loop. The `on_error` callback receives the
same protection so an error-reporting hook cannot recurse forever if it fails.

This containment applies to callback failures. It does not hide errors from the
actual tool: tool failures are still turned into `ERROR: ...` results and sent
back to the model, as in Chapter 01.

## Write a hook

Here is a small hook that reports the final number of successful tools. It
stores state on the hook instance, which is appropriate when one instance is
used for one command-line run:

```python
from lifecycle import Hooks


class ToolCounter(Hooks):
    """Count tools that completed without a host error."""

    def __init__(self):
        self.successful_tools = 0

    def after_tool_execute(self, agent, tool_name, result):
        # The agent marks failed tool calls with this string before sending
        # their result back to the model.
        if not result.startswith("ERROR:"):
            self.successful_tools += 1

    def after_loop(self, agent, output):
        # Ask the UI to render the extension's message. The hook does not
        # construct terminal colour codes or call print() itself.
        agent.ui.show_lifecycle_event(
            "tool_counter",
            f"{self.successful_tools} successful tool(s)",
        )
```

Pass it directly when using the agent from Python:

```python
from agent import agent_loop

agent_loop("write a hello world script and run it", lifecycle_hooks=ToolCounter())
```

In a larger application, a hook might write structured JSON to an audit file,
measure elapsed time around `before_brain_request` and `after_brain_response`,
or send a metric to an observability service. Keep irreversible policy checks
in the host close to the operation they protect. A hook is a useful place to
observe a proposed tool call; it is not a substitute for enforcing a security
boundary in `TOOLS` or `run()`.

## The lifecycle trace belongs to the UI

The agent tells the UI that an event occurred, for example:

```python
context.ui.show_lifecycle_event(
    "before_tool_execute",
    "write_file - 2 argument(s)",
)
```

It does not assemble colour codes or terminal strings. `UI.show_lifecycle_event`
looks up the label and style for the event in `ui.json`, builds a Rich `Text`
object, and prints it. The trace details are limited to 100 characters so a
long command, error message, or model response does not overwhelm the console.

`ui.json` now contains two maps under both `labels` and `styles`:

```json
{
  "labels": {
    "lifecycle_events": {
      "before_brain_request": "[AI] model request",
      "before_tool_execute": "[>] tool starting",
      "on_error": "[!] host error"
    }
  },
  "styles": {
    "lifecycle_events": {
      "before_brain_request": "bold magenta",
      "before_tool_execute": "bold yellow",
      "on_error": "bold red"
    }
  }
}
```

Change the labels and Rich styles to fit your workshop theme without editing
the agent loop. If a future hook has an event name not in the maps, the UI falls
back to the event name with underscores replaced by spaces.

`UI.show_hook_error()` follows the same separation. `_call_hook()` only says
which callback failed and supplies the exception; the UI selects the panel
label, title style, and border style from `ui.json`.

## Hooks around a constrained workspace

The original Chapter 01 tools wrote under `work/` and passed model text to a
host shell. Chapter 02 now routes every tool through `src/sandbox.py`:

```text
model tool request
    -> before_tool_execute hook records the requested action
    -> SandboxWorkspace or ConstrainedLocalRunner enforces host policy
    -> after_tool_execute hook records the outcome
```

`SandboxWorkspace` is the only path used by the file tools. `write_file` and
`edit_file` resolve targets only beneath repository-root `work/` or `logs/`.
They reject absolute, drive-qualified, and traversal paths that fall outside
those roots. A bare relative path such as `hello.py` goes to `work/`; a path
starting `logs/` goes to the log root. An absolute write path is allowed only
when it resolves inside one of those two roots. `read_file` remains more
permissive: it can read any readable absolute path, as well as work-relative
paths. The tool registry has no delete operation.

`ConstrainedLocalRunner` is the current implementation of the small
`SandboxRunner` interface. It does the following before starting a process:

- rejects shell operators such as `|`, `&`, `;`, `>`, and `<`;
- parses an argument list and starts it with `shell=False`;
- permits only `python` and `pytest` command variants;
- uses `work/` as the current directory;
- applies a 20-second timeout and truncates captured output.

The command result includes its exit code and bounded standard output/error, so
the model can still inspect and fix code it generated.

### The important limit

This is a **constrained local runner**, not a strong operating-system sandbox.
The child process still runs under the current user's account and is not
network-isolated. A Python process can do much more than the command parser
can express. Use trusted workshop prompts only. A future container or VM
implementation can replace `ConstrainedLocalRunner` through the same
`SandboxRunner.run()` interface, then enforce a non-root user, no network,
resource limits, and a dedicated filesystem mount.

### Sandbox audit hooks and UI status

`SandboxAuditHooks` is the default hook implementation. It appends event
records to `agent.workspace.events` rather than changing the conversation or
tool result. The host also writes every lifecycle transition as a JSON object
in a generated `.jsonl` file under `logs/`. The records include the event name,
short detail, current model step, monotonic time, and UTC timestamp. They cover
session start/stop, requested and completed tools, caught host errors, and
general loop events. `EventLog` appends each record as one line, making the
file easy to inspect or process with other tools.

The agent still owns enforcement. When it catches `SandboxPathError` or
`SandboxCommandError`, it asks the UI to show a configured status line. A
rejected command comes back to the model as an `ERROR: ...` result, which the
model can correct on its next step:

```text
sandbox | [lock] path rejected - write/edit path must stay in work or logs
lifecycle | [!] host error - tool_execute: write/edit path must stay in work or logs
```

A rejected **write or edit** target is decided in `sandbox.py`, and it is fatal
rather than a tool error the model may retry. `SandboxWorkspace.resolve_write_path()`
expands `~` and environment variables, maps `work/...` and `logs/...` onto their
roots, and refuses everything else: it prints a red `[FORBIDDEN]` banner and
raises `SandboxForbiddenError`, a subclass of `SandboxPathError`:

```text
[FORBIDDEN] write/edit path must stay in work or logs; blocked requested path: C:\Users\you\Desktop\notes.txt
[FORBIDDEN] writes are limited to work/ and logs/ - stopping the agent.
```

The banner is printed where the decision is made, so no caller can forget to
report it. `SandboxWorkspace` accepts an optional `banner` argument, which lets
tests and other hosts capture the message instead of printing it.

A relative path that names a real home or system folder is an outside request,
not a filename inside `work/`. `Desktop/notes.txt`, `~/Desktop/notes.txt`,
`%USERPROFILE%\notes.txt`, and `Users/you/notes.txt` are all refused; without
that rule Windows treats them as relative and quietly creates them under
`work/Desktop`, `work/~`, and so on.

`agent_loop()` treats `SandboxForbiddenError` as fatal. It runs the turn hooks so
the audit log records the blocked request, then raises
`SystemExit(agent.FORBIDDEN_EXIT_CODE)`, which exits with status `2`. Neither the
loop nor the interactive prompt continues, so the model never gets a chance to
retry the same request with a slightly different path. A refused command, and a
missing file, still return to the model as ordinary `ERROR: ...` results.

`UI.show_sandbox_status()` reads `sandbox_events` labels and styles from
`ui.json`, so sandbox code does not print Rich formatting directly. The labels
use portable ASCII markers such as `[box]`, `[lock]`, `[wait]`, and `[ok]`.

### Read access and write access are different

| Operation | Allowed location |
| --- | --- |
| `write_file` | `work/` or `logs/` only |
| `edit_file` | `work/` or `logs/` only |
| `read_file` | Any readable absolute path; relative paths resolve from `work/` |
| Delete | No delete tool is registered |

The resolver checks fully resolved paths, so `..` traversal and symlinks that
resolve outside both approved roots are rejected before a write or edit.

This boundary applies to the agent's registered file tools. The local runner
still starts processes as the current OS user. A Python script or pytest test
can open or delete files directly, outside the host file-tool checks. Enforcing
the same `work/` and `logs/` boundary against executed code requires a
container or VM with filesystem permissions that restrict the child process.

## Tests for extension points

`tests/test_004_agent_lifecycle.py` uses a `RecordingHooks` subclass and a mocked
model reply. It verifies that the callback sequence is ordered correctly:

```text
before_input
before_brain_request
after_brain_response
after_loop
after_input
```

It also checks that the callback receives the request and current step, and
that the captured Rich output includes lifecycle labels such as `model request`
and `agent loop finished`.

The second test uses a hook whose `before_loop()` deliberately raises an error.
The loop still receives the mocked final model response, proving that optional
extension code cannot stop the core agent merely by failing.

`tests/test_006_sandbox.py` adds coverage for the host file-tool boundary:

- safe nested workspace files can be written and read;
- writes and edits outside `work/` and `logs/` are rejected, while external
  absolute reads remain allowed;
- the agent loop rejects attempts to write/edit `README.md`, and the tool map
  has no delete operation;
- JSONL lifecycle events are written under `logs/`;
- shell operators and commands outside the allowlist never start a process;
- timeouts become model-readable errors and output is bounded;
- audit hooks record tool requests, outcomes, and caught errors;
- an unsafe path requested through the real agent loop is shown in the UI,
  returned to the model as an error, and followed by the final response.

Run the full suite from the repository root:

```powershell
uv run python -m unittest discover -s tests -v
```

- [ ] `tests/test_006_sandbox.py` verifies the constrained runner and its

The agent still has the same core ReAct loop from Chapter 01. Chapter 02 makes
that loop observable and extensible while separating host logic, extension
code, terminal presentation, and file-tool policy. The current process runner
does not isolate executed code from the operating system.
