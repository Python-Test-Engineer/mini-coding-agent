Chapter 01 / Agent foundations

A coding agent is a loop.

A model proposes the next action. Python executes it, returns the result, and asks the model what to do next.

01Separate model decisions from host execution.
02Trace a tool call through the message history.
03See where the demo stops being safe or complete.
01 / MODEL
The central idea

Decide. Execute. Feed back.

The model does not run Python functions. It returns a proposal; the host program decides which registered tool to call and sends the result back in the next request.

02 / TOOLS
The host's capabilities

Four functions. One small toolbox.

An agent can only do what its host exposes. The tool registry in agent.py maps the model's requested name to a Python function.

Tool What the host does
write_file(path, content) Writes text to a file under the working directory by default.
edit_file(path, old, new) Replaces the first matching occurrence in a file.
read_file(path) Reads a file and returns its text.
run(command) Runs in root work/; returns stdout, or stderr if stdout is empty (not the exit code).
Important · not a sandbox

The agent always uses the repository-root work/ directory, even if launched from src/. But file paths are not contained there, and run() uses shell=True. Commands run with the user's permissions. Use trusted prompts only.

03 / HANDOFF
Who does what?

The model asks. The host acts.

Tool schemas advertise available functions in the chat request. A schema is an interface description—not permission for the model to execute code on its own.

  1. Describe toolsThe request includes JSON schemas: names, arguments, and required fields.
  2. Receive a proposalThe assistant response names a tool and provides JSON arguments.
  3. Dispatch in PythonThe host decodes arguments and calls the matching function in TOOLS.
  4. Return the resultThe host adds a role: "tool" message with the matching call ID.
OpenAI-compatible schemawrite_file
{
  "type": "function",
  "function": {
    "name": "write_file",
    "parameters": {
      "type": "object",
      "properties": {
        "path": { "type": "string" },
        "content": { "type": "string" }
      },
      "required": ["path", "content"]
    }
  }
}
04 / HISTORY
The loop's working memory

Every turn is sent again.

The chat API is stateless. The agent keeps the conversation in a Python list and resends that history with each request, including assistant tool calls and host results.

01 · START

System + user

The instructions and request form the first message history.

02 · PROPOSE

Assistant tool call

The model asks for a tool and gives it a unique call ID.

03 · EXECUTE

Host runs function

The Python process executes the registered function and captures a result.

04 · REPLY

Tool message

The result is added with tool_call_id so it matches the request.

05 · REPEAT

Send history again

The model sees what happened and can request another action.

06 · FINISH

No more tools

A response without tool calls ends the loop; eight steps is the maximum.

assistant
tool call: write_file(...), ID call_01
tool
tool_call_id: call_01 · Created hello.py
assistant
final answer with no tool_calls · the loop ends

06 / OUTPUT
What the user sees

Rich makes the loop legible.

UI renders the request, model text, tool calls, code, results, and final status. The footer is wired to usage data returned by the API.

CONTEXT ESTIMATELatest prompt_tokens. A percentage appears only if the response includes context_limit.

If a provider omits usage fields, the app keeps the last available values. Tests use fixed responses and do not need a live API key.

Chapter 02 / Extension points

Hooks make the loop observable.

A hook is a named callback at a useful boundary in the agent loop. It records what the host is doing without taking ownership of model requests, tool execution, or terminal rendering.

01Place callbacks around clear lifecycle boundaries.
02Inspect a turn through a small, documented context object.
03Use hooks to audit a constrained tool host.
01 / IDEA
An implemented extension

Hooks are named points around work.

A hook runs when the host reaches a defined event—for example, before a model request or after a tool returns. The hook can inspect context, record an event, or apply a policy; it should not silently replace the agent's control flow.

Implemented in Chapter 02

src/lifecycle.py defines the callback contract and src/agent.py sends notifications around a real model and tool run. The existing loop and tools retain control of work.

02 / CONTRACT
One documented interface

Each callback sees the current turn.

Hooks is a no-op base class in src/lifecycle.py. Students override only the callbacks they need. Each receives an AgentContext with the request, live message history, usage metrics, active UI, contained workspace, and current model step.

CallbackWhen it firesExtra data
before_input / after_inputA request starts and finishes.User input and final output.
before_loop / after_loopThe model/tool loop starts and ends.Final output on completion.
before_brain_requestImmediately before chat(messages).The live conversation list.
after_brain_responseImmediately after a provider response.The provider message dictionary.
before_tool_execute / after_tool_executeBefore and after every requested tool.Tool name, arguments, and result.
on_errorThe host catches malformed tool arguments or a tool error.Error object and phase.
Future boundaries already named

The contract also reserves context compaction, mode-change, and provider-switch callbacks. This agent does not yet perform those actions, so it does not fire those events.

03 / WIRING
The host still controls work

Call hooks around the real transitions.

A small, ordered lifecycle is easier to test than callbacks scattered through tool code. Each event says what data is available while the host continues to own requests, dispatch, and results.

01 · BEFORE REQUEST

Start the turn

before_input and before_loop announce the request and create its context.

02 · AFTER RESPONSE

Ask the model

before_brain_request sees the live messages; after_brain_response sees the reply.

03 · BEFORE TOOL

Start each tool

before_tool_execute receives the requested tool name and decoded arguments.

04 · AFTER TOOL

Finish each tool

after_tool_execute receives both successful results and host-created error results.

05 · BEFORE REPEAT

Report caught errors

on_error observes malformed arguments and tool exceptions caught by the host.

06 · ON FINISH

Close the turn

after_loop and after_input run for a final answer or the step limit.

04 / OUTPUT
UI owns presentation

Make lifecycle work visible without printing from hooks.

agent.py supplies an event name and a short detail. The UI chooses the terminal text, colour, and error panel through ui.json.

UI configurationWhat it controls
labels.lifecycle_eventsThe marker and wording for each callback, such as [AI] model request.
styles.lifecycle_eventsThe Rich colour for each event: model calls are magenta and tools are yellow.
show_lifecycle_event()Builds the compact trace line and limits details to 100 characters.
show_hook_error()Displays a configured error panel when optional extension code raises an exception.
Portable console markers

The event markers use ASCII forms such as [AI], [>], and [ok]. They remain readable in legacy Windows consoles while Rich adds colour where the terminal supports it.

Contain extension failures

If a callback raises an exception, the host renders a lifecycle-hook error panel and continues the core loop. A failing optional observer cannot stop a model response or tool result.

Keep the loop visible

The model proposes, Python executes, and hooks observe. The trace makes those boundaries easier to follow without placing terminal formatting in agent logic.

05 / SANDBOX
The host enforces the boundary

Hooks audit a constrained workspace.

Hooks report requested work and its outcome. SandboxWorkspace and ConstrainedLocalRunner enforce the file and process rules immediately where work happens.

ComponentHost-enforced behaviour
SandboxWorkspaceAllows only relative paths that resolve under root sandbox-work/.
Path policyRejects absolute, drive-qualified, and parent-traversal paths before any file operation.
ConstrainedLocalRunnerUses shell=False, an allowlist, a timeout, and bounded output.
SandboxAuditHooksRecords sandbox session, requested tool, completed tool, and caught-error events.
Constrained is not isolated

The runner still starts processes under the current user and does not disable their network access. It is appropriate only for trusted workshop prompts. A container or VM runtime is needed for a security boundary.

Unsafe path through the real loophost error
tool read_file({"path": "../outside.txt"})
sandbox | [lock] path rejected - path escapes the sandbox workspace
lifecycle | [!] host error - tool_execute: path escapes the sandbox workspace
result ERROR: path escapes the sandbox workspace

UI.show_sandbox_status() formats these status lines from the sandbox_events labels and styles in ui.json. The sandbox module itself does not print terminal formatting.
