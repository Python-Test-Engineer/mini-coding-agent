Complete workshop book

How mini-coding-agent works

src/agent.py implements a small, working agentic coding loop. The model chooses tools, Python executes them, and the results return to the model. It demonstrates the core pattern used by coding agents without an agent framework or LLM SDK. The agent uses rich for its console interface; HTTP, JSON, filesystem, and process operations use the Python standard library.

The app lives in src/. agent.py owns the OpenRouter request, tool functions, agent loop, and usage tracking. ui.py renders the console and footer. ui.json configures its labels and Rich styles. tests/ contains the unittest suite. work/ is the intended working directory for generated files and commands. demo-prompt.md contains a sample request. The root main.py is only a greeting stub. Launch the actual agent with src/agent.py.

The point is to show what an agent actually is. It is not one magic LLM call, but a loop. The model decides what to do, the host executes it, and the result returns to the model. This repeats until the model stops asking for tools.

request ─▶ [ model response ] ─▶ tool call ─▶ host runs it ─▶ result ─▶ [ model response ]
                                      ▲                                           │
                                      └──────────── loop (max 8 steps) ──────────┘
                                                 ...no more tools ▶ done

The four tools the agent can use

An agent can only do whatever its host exposes. Here, exactly four functions are exposed. work/ is the intended working directory, but not a security sandbox:

Tool Signature What it does
write_file (path, content) Write text to a file path
edit_file (path, old, new) Replace the first occurrence of old in a file
read_file (path) Return a file's text contents
run (command) Run a shell command with work/ as its current directory

The agent anchors WORKDIR to the repository root. It can create work/hello.py even when launched from src/, then run python hello.py. It can inspect the output, edit the script, and run it again to complete a fix cycle. run() uses work/ as the command's current directory. It returns stdout, or stderr when stdout is empty. It does not report the process exit code.

Security note: work/ is only the default working directory, not a sandbox. File tools do not check that paths stay inside it, and run() uses shell=True, so commands can access files and run programs outside it. Use only with trusted prompts in a controlled demo; do not expose this app to untrusted users or treat it as a secure coding agent.

How the loop gets the model to call tools

Modern chat models understand tools as part of their training. You advertise the available functions as a JSON schema in the API request, exactly like this:

{
  "type": "function",
  "function": {
    "name": "write_file",
    "description": "Create or overwrite a file in the work dir.",
    "parameters": {
      "type": "object",
      "properties": { "path": {"type": "string"}, "content": {"type": "string"} },
      "required": ["path", "content"]
    }
  }
}

When the model requests a tool, its reply contains a tool_calls array describing which function and what arguments — it does not execute anything itself. That's the crucial separation:

  1. The model proposes: "call write_file with these args."
  2. The host executes the actual filesystem/system call.
  3. The host appends a role: "tool" message containing the result.
  4. The model sees the result and returns another response, either requesting more tools or ending the loop.

The model does not execute Python functions itself, but the host executes its requested operations with the permissions of the user running the app. This separation is how tool calling works; it is not a security boundary.

The message history that drives it

The API is stateless: each request is a batch of messages. agent.py keeps the conversation in a plain list and resends it with each request:

system   You are a minimal coding agent...
user     write a hello world script and run it
assistant  <text>      (rendered with the thought label configured in ui.json)
assistant  <tool_calls: write_file(path, content)>
tool      Created hello.py                  ← result, matched by tool_call_id
assistant  <tool_calls: run(python hello.py)>
tool      Hello, world!                     ← output of the script
assistant  <final answer, no tool_calls>    → loop ends

Two details worth noticing:

  • Tool results carry an id. Each assistant tool_call has an id; the host echoes it on the corresponding tool message so the model can pair them.
  • The loop ends when the model returns no tool_calls. The app also stops after at most eight model-response iterations for that request (max_steps=8), even if the model keeps requesting tools.

The HTML "memory" demo stores chat text in localStorage. Here, the entire tool conversation is the working memory. The app resends it each iteration, so the agent can remember what it wrote earlier.

That working memory now spans follow-up requests too. When the model gives a final answer, agent_loop() adds it to the history. The outer conversation loop then asks for another request and adds it as a new user message. Each follow-up can refer to earlier requests, answers, and tool results. The eight-step limit applies to each request; usage totals accumulate across the interactive conversation. Type exit or quit to finish, or end input with Ctrl+C or EOF.

Configuration & the API call

  • agent.py loads the project-root .env with python-dotenv and leaves existing process environment variables untouched. The file supplies OPENROUTER_API_KEY and optionally MODEL; the model falls back to deepseek/deepseek-v4.1-flash when unset.
  • agent.py sends an HTTP POST to https://openrouter.ai/api/v1/chat/completions using urllib.request. The JSON request contains the selected model, message history, and tool schemas. The system prompt asks the model to work step by step, run and fix its code, and finish with a short plain-text summary.

Console UI and configuration

How ui.py uses Rich

ui.py defines a UI class around Rich's Console. Rich handles terminal layout and styling so the app can show structured output rather than plain, unformatted log lines. The UI can use the default console or accept a Console and config path when constructed. By default, it reads ui.json from beside ui.py as UTF-8 JSON, then uses its labels and styles dictionaries.

Each UI method renders one part of the interaction:

  • prompt() builds a Rich Text prompt from the model name, request label, and indicator, then uses Console.input() to read the user's request.
  • show_start() draws a Console.rule() header and puts the request in a Panel; show_thought() displays the model's text in a step-labelled panel.
  • show_tool() builds a Text line with the tool name and JSON arguments.
  • show_code() uses Rich Syntax to display file content with Python highlighting and the configured theme.
  • show_result() puts tool output in a result Panel; show_done() and show_max_steps() render the completion and step-limit messages, then call footer() to show token and cost usage.
  • footer() shows the latest prompt size, totals for prompt and completion tokens, and cumulative cost. It shows context-window percentage only when a context limit is available; otherwise it labels the limit as unavailable.

Rich components take styles separately from their text. For example, a Panel has title and border styles. A Text object can style individual spans. This lets the interface highlight the model prompt, tools, code and results without mixing terminal escape codes into agent logic.

What ui.json controls

ui.json is the UI's visual and wording configuration, not the agent's behavior. Its labels values supply the text shown by ui.py; {model} is substituted into the model prompt label and {step} into the thought-panel title. Its styles values are Rich style strings. For example, bold cyan sets bold cyan text, and yellow sets a panel border color. monokai selects the syntax-highlighting theme used by Syntax.

The keys are looked up directly by ui.py. Keep their names and format placeholders when changing the JSON. Edit values to rename the prompt, header, tool/result labels, or status messages. You can also change colors and highlighting without changing the agent loop. Invalid JSON, missing keys, or an unsupported Rich style can prevent the UI from starting.

Running it

cd src
uv run agent.py "write a hello world script and run it"
# or: omit the request to start with an interactive prompt
# or override: MODEL=openai/gpt-4o-mini OPENROUTER_API_KEY=sk-or-... uv run agent.py "..."

The root pyproject.toml declares Python 3.11+ and the project dependencies. uv run installs them into the project environment when needed. You can launch the app from src/, as shown above. WORKDIR is anchored to the repository root, so generated files and shell commands always use root-level work/. If no request is supplied on the command line, ui.py prompts for one and displays the selected model name. After each answer, the app prompts for another request and keeps the same conversation history.

When run without a command-line request, the prompt starts with the active model name, for example: [deepseek/deepseek-v4.1-flash] Request ›. It uses the same model resolution as the API call: process environment, project-root .env, then the built-in fallback. With a command-line request, the agent handles it first and then prompts for follow-ups. Enter exit or quit to end the conversation; blank requests are ignored.

Watch the terminal: you'll see the model's text, each tool write_file({...}) call, the result panels, and the final response. The log makes each loop step visible as the app runs.

Usage metrics and tests

Each chat-completions response may include a usage object. agent.py reads prompt_tokens, completion_tokens, and cost from it. Prompt and completion tokens and cost accumulate across model calls. The latest prompt-token count is the current context estimate. If a response omits usage fields, the app keeps the last available values. The footer does not assume a context limit. It shows a percentage only when the response provides context_limit.

The tests live in the root tests/ directory and use Python's standard-library unittest. They capture Rich output and replace the network call with a fixed response. The suite therefore makes no OpenRouter request and requires no API key. From the repository root, run it with the project environment:

uv run python -m unittest discover -s tests -v

What a fuller agent adds (the demo's roadmap)

This is deliberately minimal. Production coding agents bolt on:

  • More tools (read directories, run tests, git, web search) and richer tool result handling.
  • A real sandbox — execute untrusted code in a container/VM, not subprocess.
  • Context trimming — the full history is re-sent each step, so long runs blow up token costs; real agents summarize or drop old turns.
  • A planner / multi-agent split — separate the "what to do" reasoning from the "which files to touch" execution.
  • Human-in-the-loop — pause and ask before destructive commands.

The loop shape here — decide, execute, feed back, repeat — is the thing they all share.

Chapter 02 - Lifecycle hooks and an observable agent loop

Chapter 01 built a small coding agent: a model requests tools, the Python host runs them, and tool results return to the model. The loop works, but it is hard to extend cleanly when every new feature must be inserted directly into the middle of agent_loop().

This chapter adds lifecycle hooks. A hook is a named callback that runs at a defined point in the host-controlled agent lifecycle. Hooks are useful for observing an agent, recording metrics, adding audit events, playing a sound, or connecting later workshop exercises without rewriting the loop.

The goal is not to give callback code control over the agent. The host still owns model requests, tool execution, error handling, and console rendering. Hooks receive information about the transition and can react to it.

src/agent.py Now only the host loop: the turn context, hook dispatch, agent_loop(), and main(). The model call, the tool functions, and every printed line live elsewhere.
src/lifecycle.py New Hooks base class that documents every callback point.
src/ui.py Adds Rich rendering methods for lifecycle trace lines, hook failures, the red [FORBIDDEN] banner, and the session hint.

src/sounds.json Declares the sound effects. Each entry records its sound_file, a play flag, and the location it fires from.

One file, one job

Chapter 01 kept the model call and the four tool functions inside agent.py, because the whole point was to see one file do the work. Growing that agent then meant editing the same file for every new feature. This chapter moves those two jobs into modules of their own, so the loop stays short: agent.py owns when something happens, and the other files own how:

main()                       interactive session; session hooks wrap every turn
  └─ agent_loop()            one request: think → tool call → result → repeat
       ├─ brain.chat()             ask the model and read the billed usage
       ├─ tools.bind_tools()       the four tools the model may request
       ├─ sandbox.py               enforce paths and commands where they run
       ├─ lifecycle.py             optional observers of each transition
       ├─ ui.py + ui.json          every line the user sees, and its wording
       ├─ sounds.py + sounds.json  the sound effects, and whether each plays
       └─ agent_logging.py         the JSONL audit trail under logs/
Module Question it answers
src/agent.py When does each step happen, and in what order?
src/brain.py How do we talk to the model, and what may it ask for?
src/tools.py Which host functions can the model request by name?
src/sandbox.py Is this file path or command allowed?
src/lifecycle.py Who wants to observe this transition?
src/ui.py, src/ui.json How does this look in the terminal?
src/sounds.py, src/sounds.json Which sound plays, and is it enabled?
src/agent_logging.py What is written to the audit trail?

Two rules keep the split honest. First, agent.py contains no print() and no Rich code: it reports events to the UI, and the UI decides their appearance. Second, the loop contains no policy: it calls a tool and receives either text or an exception, and sandbox.py decides which. Both rules are what let you replace a module - a container runner instead of the local runner, another provider instead of OpenRouter - without editing the loop.

Run the agent as before:

cd src
uv run agent.py "write a hello world script and run it"

The terminal now includes lines similar to these between the request panel and the model/tool output:

lifecycle | [*] agent loop started - waiting for a model response
lifecycle | [AI] model request - step 1 - 2 messages
lifecycle | [AI] model response - step 1 - 1 tool call(s)
lifecycle | [>] tool starting - write_file - 2 argument(s)
lifecycle | [ok] tool finished - write_file - complete
sandbox | [box] constrained local runner - writes: work/ and logs/; no host shell

The markers are deliberately ASCII rather than emoji. They remain readable in legacy Windows terminals that cannot encode every Unicode symbol. Rich supplies the colour; ui.json supplies the text and colour choices.

Why hooks belong at lifecycle boundaries

Without hooks, an extra feature is tempted to reach into unrelated places in the loop:

# This quickly makes the loop difficult to read and test.
save_audit_record(prompt)
reply = chat(messages)
save_model_response(reply)
result = tools[name](**args)
save_tool_result(result)

The loop should instead announce the transitions it already performs:

request
  -> before_input
  -> before_loop
  -> before_brain_request
  -> after_brain_response
  -> before_tool_execute / after_tool_execute (zero or more times)
  -> after_loop
  -> after_input

This makes each responsibility clear:

Responsibility Owner
Deciding when an event happened and executing tools src/agent.py
Asking the model, and describing the tools it may request src/brain.py
Implementing the tools the model may request by name src/tools.py
Deciding whether a path or command is allowed src/sandbox.py
Reacting to an event A Hooks subclass in the application
Choosing how an event looks in the terminal UI and ui.json
Declaring which sound plays, and whether it is enabled sounds.py and sounds.json
Recording the audit trail src/agent_logging.py

For example, a hook can count completed tools, but it does not replace the tool result that is sent back to the model. That keeps the model/tool protocol in one trustworthy place: the host loop.

The hook contract in src/lifecycle.py

lifecycle.py contains a small base class. On Windows, its session-start hook plays %WINDIR%\Media\Windows Logon.wav asynchronously when the file exists. The WAV path and its play flag are read from sounds.json through sounds.py, so the jingle can be silenced or repointed with a config edit instead of a code change. Other methods are no-ops by default, so a subclass only overrides the callbacks it needs. The default SandboxAuditHooks calls the base session-start hook before writing its session log entry.

class Hooks:
    def before_tool_execute(self, agent, tool_name, arguments):
        """Called before a requested tool is executed."""

    def after_tool_execute(self, agent, tool_name, result):
        """Called after a requested tool finishes, including failures."""

The agent parameter is an AgentContext created for one call to agent_loop(). It exposes state that is useful to an observer:

Context attribute Meaning
request The original user request text.
messages The live message list that will be sent to the model.
metrics The token and cost dictionary used by the footer.
ui The active UI instance. A hook normally should not render directly.
workspace The file-path policy and JSONL lifecycle event log.
step The current one-based model-response step.

The current lifecycle callbacks are:

Callback Called when Extra arguments
on_session_start The interactive conversation starts; on Windows, the base hook plays Windows Logon.wav when present. None
on_session_stop The interactive conversation ends. None
before_input A request starts processing. user_input
after_input A request has finished processing. user_input, output
before_loop The model/tool loop begins. None
after_loop The model/tool loop ends. output
before_brain_request Just before chat(messages). conversation
after_brain_response Just after a model reply is read. thought
before_tool_execute Just before a requested tool runs. tool_name, arguments
after_tool_execute Just after that tool returns or fails. tool_name, result
on_error The host catches a tool or tool-argument error. error, phase

The base class also reserves before_compact, after_compact, on_mode_change, and on_brain_switch. They are not fired by the Chapter 02 agent because it does not compact context, support modes, or switch providers. Keeping their names in one documented contract gives later chapters stable places to add those features.

Calling hooks from the agent loop

agent.py imports the contract and creates a default instance:

from sandbox import SandboxAuditHooks

# The default hook records sandbox session, tool, and caught-error events.
hooks = SandboxAuditHooks()

The agent_loop() function also accepts lifecycle_hooks. This makes tests and other Python callers independent of the module-level default:

def agent_loop(
    prompt: str,
    max_steps: int = 8,
    lifecycle_hooks: Hooks | None = None,
) -> None:
    active_hooks = lifecycle_hooks if lifecycle_hooks is not None else hooks

At the start of a turn, the agent builds its messages and context, then reports the first two transitions:

context = AgentContext(prompt, messages, metrics, ui, WORKSPACE)
_call_hook(active_hooks, "before_input", context, prompt, detail="...")
_call_hook(active_hooks, "before_loop", context, detail="...")

Before each request, the loop gives the hook the same messages list it is about to pass to chat(). After the reply, it gives the hook the provider message dictionary. The hook therefore sees the actual conversation state and tool calls, not a copied or reconstructed version.

The tool map itself is built once per turn, from the workspace and runner the loop is using:

# agent.py - the loop keeps the map and the enforcing objects in step.
tools = bind_tools(context.workspace, RUNNER)

bind_tools() lives in src/tools.py. It returns a dictionary whose keys match the tool names in brain.TOOL_SCHEMAS and whose values already have the host objects attached, so the loop only supplies what the model sent:

# tools.py - functools.partial attaches the enforcing object.
return {
    "write_file": partial(write_file, workspace),
    "edit_file": partial(edit_file, workspace),
    "read_file": partial(read_file, workspace),
    "run": partial(run, runner),
}

For each requested tool, the sequence is:

_call_hook(active_hooks, "before_tool_execute", context, name, args)
try:
    result = tools[name](**args)
except Exception as error:
    _report_error(active_hooks, context, error, "tool_execute")
    result = f"ERROR: {error}"
_call_hook(active_hooks, "after_tool_execute", context, name, result)

after_tool_execute runs whether the tool succeeded or failed. That is useful for monitoring because an audit record can show both the requested action and its final outcome.

Hook failures are contained

Extensions should not make the coding agent unusable. _call_hook() catches an exception raised by a callback and asks the UI to show a lifecycle-hook error panel. It then continues the host loop. The on_error callback receives the same protection so an error-reporting hook cannot recurse forever if it fails.

This containment applies to callback failures. It does not hide errors from the actual tool: tool failures are still turned into ERROR: ... results and sent back to the model, as in Chapter 01.

Write a hook

Here is a small hook that reports the final number of successful tools. It stores state on the hook instance, which is appropriate when one instance is used for one command-line run:

from lifecycle import Hooks


class ToolCounter(Hooks):
    """Count tools that completed without a host error."""

    def __init__(self):
        self.successful_tools = 0

    def after_tool_execute(self, agent, tool_name, result):
        # The agent marks failed tool calls with this string before sending
        # their result back to the model.
        if not result.startswith("ERROR:"):
            self.successful_tools += 1

    def after_loop(self, agent, output):
        # Ask the UI to render the extension's message. The hook does not
        # construct terminal colour codes or call print() itself.
        agent.ui.show_lifecycle_event(
            "tool_counter",
            f"{self.successful_tools} successful tool(s)",
        )

Pass it directly when using the agent from Python:

from agent import agent_loop

agent_loop("write a hello world script and run it", lifecycle_hooks=ToolCounter())

In a larger application, a hook might write structured JSON to an audit file, measure elapsed time around before_brain_request and after_brain_response, or send a metric to an observability service. Keep irreversible policy checks in the host close to the operation they protect. A hook is a useful place to observe a proposed tool call; it is not a substitute for enforcing a security boundary in the tool functions of src/tools.py or in run().

The lifecycle trace belongs to the UI

The agent tells the UI that an event occurred, for example:

context.ui.show_lifecycle_event(
    "before_tool_execute",
    "write_file - 2 argument(s)",
)

It does not assemble colour codes or terminal strings. UI.show_lifecycle_event looks up the label and style for the event in ui.json, builds a Rich Text object, and prints it. The trace details are limited to 100 characters so a long command, error message, or model response does not overwhelm the console.

ui.json now contains two maps under both labels and styles:

{
  "labels": {
    "lifecycle_events": {
      "before_brain_request": "[AI] model request",
      "before_tool_execute": "[>] tool starting",
      "on_error": "[!] host error"
    }
  },
  "styles": {
    "lifecycle_events": {
      "before_brain_request": "bold magenta",
      "before_tool_execute": "bold yellow",
      "on_error": "bold red"
    }
  }
}

Change the labels and Rich styles to fit your workshop theme without editing the agent loop. If a future hook has an event name not in the maps, the UI falls back to the event name with underscores replaced by spaces.

UI.show_hook_error() follows the same separation. _call_hook() only says which callback failed and supplies the exception; the UI selects the panel label, title style, and border style from ui.json.

Two more lines come from the same place. UI.show_forbidden() renders the red [FORBIDDEN] banner that src/sandbox.py asks for when it blocks a write or edit, and UI.show_hint() renders the one-line "type exit or quit" message main() shows when a session starts. Neither string is written in the loop, so renaming or recolouring either one means editing ui.json alone.

Hooks around a constrained workspace

The original Chapter 01 tools wrote under work/ and passed model text to a host shell. Chapter 02 now routes every tool through src/sandbox.py:

model tool request (name + JSON arguments)
    -> agent_loop resolves the name in the tool map built by tools.bind_tools()
    -> before_tool_execute hook records the requested action
    -> SandboxWorkspace or ConstrainedLocalRunner enforces host policy
    -> after_tool_execute hook records the outcome

SandboxWorkspace is the only path used by the file tools. write_file and edit_file resolve targets only beneath repository-root work/ or logs/. They reject absolute, drive-qualified, and traversal paths that fall outside those roots. A bare relative path such as hello.py goes to work/; a path starting logs/ goes to the log root. An absolute write path is allowed only when it resolves inside one of those two roots. read_file remains more permissive: it can read any readable absolute path, as well as work-relative paths. The tool registry has no delete operation.

ConstrainedLocalRunner is the current implementation of the small SandboxRunner interface. It does the following before starting a process:

  • rejects shell operators such as |, &, ;, >, and <;
  • parses an argument list and starts it with shell=False;
  • permits only python and pytest command variants;
  • uses work/ as the current directory;
  • applies a 20-second timeout and truncates captured output.

The command result includes its exit code and bounded standard output/error, so the model can still inspect and fix code it generated.

The important limit

This is a constrained local runner, not a strong operating-system sandbox. The child process still runs under the current user's account and is not network-isolated. A Python process can do much more than the command parser can express. Use trusted workshop prompts only. A future container or VM implementation can replace ConstrainedLocalRunner through the same SandboxRunner.run() interface, then enforce a non-root user, no network, resource limits, and a dedicated filesystem mount.

Sandbox audit hooks and UI status

SandboxAuditHooks is the default hook implementation. It appends event records to agent.workspace.events rather than changing the conversation or tool result. The host also writes every lifecycle transition as a JSON object in a generated .jsonl file under logs/. The records include the event name, short detail, current model step, monotonic time, and UTC timestamp. They cover session start/stop, requested and completed tools, caught host errors, and general loop events. EventLog appends each record as one line, making the file easy to inspect or process with other tools.

The agent still owns enforcement. When it catches SandboxPathError or SandboxCommandError, it asks the UI to show a configured status line. A rejected command comes back to the model as an ERROR: ... result, which the model can correct on its next step:

sandbox | [lock] path rejected - write/edit path must stay in work or logs
lifecycle | [!] host error - tool_execute: write/edit path must stay in work or logs

A rejected write or edit target is decided in sandbox.py, and it is fatal rather than a tool error the model may retry. SandboxWorkspace.resolve_write_path() expands ~ and environment variables, maps work/... and logs/... onto their roots, and refuses everything else: it asks the UI for a red [FORBIDDEN] banner and raises SandboxForbiddenError, a subclass of SandboxPathError:

[FORBIDDEN] write/edit path must stay in work or logs; blocked requested path: C:\Users\you\Desktop\notes.txt
[FORBIDDEN] writes are limited to work/ and logs/ - stopping the agent.

The banner is announced where the decision is made, so no caller can forget to report it, but its appearance is still the UI's: the default banner calls UI.show_forbidden(), which reads the two lines and their colour from ui.json. Policy code contains no Rich code. On Windows, every sandbox policy rejection plays C:\Windows\Media\tada.wav. For a rejected write/edit, the sound plays immediately after the [FORBIDDEN] banner; rejected command syntax and drive-relative read paths play it at their policy check too. Playback is synchronous and best-effort: a missing WAV file or audio device does not affect enforcement. Like the session-start jingle, the alert WAV and its play flag are declared in sounds.json and played through sounds.py. SandboxWorkspace accepts an optional banner argument, which lets tests and other hosts capture the message instead of printing it.

A relative path that names a real home or system folder is an outside request, not a filename inside work/. Desktop/notes.txt, ~/Desktop/notes.txt, %USERPROFILE%\notes.txt, and Users/you/notes.txt are all refused; without that rule Windows treats them as relative and quietly creates them under work/Desktop, work/~, and so on.

agent_loop() treats SandboxForbiddenError as fatal. It runs the turn hooks so the audit log records the blocked request, then raises SystemExit(agent.FORBIDDEN_EXIT_CODE), which exits with status 2. Neither the loop nor the interactive prompt continues, so the model never gets a chance to retry the same request with a slightly different path. A refused command, and a missing file, still return to the model as ordinary ERROR: ... results.

UI.show_sandbox_status() reads sandbox_events labels and styles from ui.json, so sandbox code does not print Rich formatting directly. The labels use portable ASCII markers such as [box], [lock], [wait], and [ok].

Read access and write access are different

Operation Allowed location
write_file work/ or logs/ only
edit_file work/ or logs/ only
read_file Any readable absolute path; relative paths resolve from work/
Delete No delete tool is registered

The resolver checks fully resolved paths, so .. traversal and symlinks that resolve outside both approved roots are rejected before a write or edit.

This boundary applies to the agent's registered file tools. The local runner still starts processes as the current OS user. A Python script or pytest test can open or delete files directly, outside the host file-tool checks. Enforcing the same work/ and logs/ boundary against executed code requires a container or VM with filesystem permissions that restrict the child process.

Tests for extension points

tests/test_004_agent_lifecycle.py uses a RecordingHooks subclass and a mocked model reply. It verifies that the callback sequence is ordered correctly:

before_input
before_brain_request
after_brain_response
after_loop
after_input

It also checks that the callback receives the request and current step, and that the captured Rich output includes lifecycle labels such as model request and agent loop finished.

The second test uses a hook whose before_loop() deliberately raises an error. The loop still receives the mocked final model response, proving that optional extension code cannot stop the core agent merely by failing.

tests/test_006_sandbox.py adds coverage for the host file-tool boundary:

  • safe nested workspace files can be written and read;
  • writes and edits outside work/ and logs/ are rejected, while external absolute reads remain allowed;
  • the agent loop rejects attempts to write/edit README.md, and the tool map has no delete operation;
  • JSONL lifecycle events are written under logs/;
  • shell operators and commands outside the allowlist never start a process;
  • timeouts become model-readable errors and output is bounded;
  • audit hooks record tool requests, outcomes, and caught errors;
  • an unsafe path requested through the real agent loop is shown in the UI, returned to the model as an error, and followed by the final response.
